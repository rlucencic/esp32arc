# ARM2 immediate-operand table experiment

Baseline: shared core `353344c` (CPU source unchanged from `96fd93c`).
Physical Tab5: ESP32-P4 rev. 1.0 at 360 MHz, ESP-IDF 5.5.6, GCC 14.2.0,
`-O2`. Both hardware comparisons select A440/ARM2 at 8 MHz, RISC OS 3.11,
4 MB RAM and sound enabled. Lander leaves measurable idle CPU time while
holding a paced 50 FPS on this model.

## Candidate

ARM2 immediate data-processing operands encode an eight-bit value and a
four-bit rotation count, with the byte rotated right by twice that count.
The baseline computes the result with shifts and a rotate-zero check.
The candidate looks up the decoded value using the operand's low twelve
bits. Shifter carry still preserves incoming C for a zero rotation and
uses bit 31 of the decoded value for nonzero rotations. Arithmetic flag
logic and guest cycle accounting are unchanged.

The 4,096-entry constant table is generated by compile-time macros. The
zero-rotation macro avoids any shift by 32. There is no runtime table
initialization routine. The existing core linker mapping places the table
in internal RAM, rather than a flash-cache lookup.

The linked ELF contains `s_immediate` at `0x4ff44100` in `.dram1.data`.
All 4,096 words match the expected decoded values. It costs **16,384
bytes of internal data RAM**. `arm2_run` shrinks from 43,154 to 43,018 bytes
(-136). Its indirect jump-site count remains 88; register allocation,
code layout and data addresses may still change.

The established deterministic Lander mix has 18.1% immediate
instructions. Host reporting now counts nonzero rotation fields: 5,814,243
operands, 36.4% of immediate instructions, use a nonzero rotation. The
remaining 63.6% use zero rotation, for which the baseline already has a
short path. The experiment tests the full table's overall tradeoff.

## Correctness

- All 190 CPU checks pass.
- All 100,000 randomized instructions agree with Unicorn, seed 1.
- All 4,096 immediate encodings, both incoming carry values and three
  upper-opcode patterns pass an independent integer-arithmetic oracle:
  24,576 decoded-value and shifter-carry checks against the actual private
  `operand2` helper.
- Every table word in the linked target ELF matches the expected value;
  its internal-RAM section and address are recorded.
- The deterministic A3020 host replay still executes 88,360,660 instructions
  in frames 9,000–10,000 and produces screenshot SHA256
  `9e9f915326be41b8cb7485beac45621e255ccade404f5b18a4e55e9011392104`.

The helper check rebuilds committed baseline `353344c` with the saved
candidate patch in a temporary directory using the host C compiler:

```sh
python3 docs/measurements/immediate-table-2026-11-06/check_immediates.py
```

An optional argument selects another `esp32emu` checkout. This check
requires no saved binary or Unicorn installation. After building the
candidate for P4, its table can also be checked with an environment that
has pyelftools installed:

```sh
python3 docs/measurements/immediate-table-2026-11-06/check_target_table.py build-tab5/esp32arc.elf
```

## Hardware method

Both builds start Lander from the same applications disc, warm up,
measure frame progress over 30 seconds and receive five separate
32,000-sample core 1 profiles at 20 kHz. Timing and profiling are separate.
Residency percentages measure interpreter CPU time at a paced frame
rate, not uncapped FPS. Both builds are measured in this session.

The candidate booted much more slowly. The fixed launch schedule did not
reach Lander's game video mode in time; the timing helper correctly
rejected that first attempt. After an additional wait, the launch command
was repeated and 320x256 8 bpp game mode was confirmed before timing and
profiling.
The candidate measurements below come from that recovered game run.

| A440 Lander | Baseline | Immediate table |
| --- | --- | --- |
| Frame-count interval | 1,503 / 30.062 s | 696 / 30.039 s |
| Frame rate | 49.996 FPS | 23.170 FPS |
| Real-time speed | 99.992% | 46.340% |
| ARM2 residency captures | 68.9%, 69.0%, 68.9%, 68.0%, 68.9% | 90.2%, 89.6%, 89.9%, 90.2%, 89.9% |

## Disposition

**Rejected.** Lander falls to **23.170 FPS**, 46.340% real time, versus
approximately 50 FPS for the baseline. Candidate ARM2 residency averages
89.96% versus 68.74%, but these percentages are observed at different
frame rates and should not be read as a direct per-frame cost comparison.
The throughput loss is the decisive result.

The target startup log confirms a 360 MHz CPU clock and a page table in
internal RAM. The 16 KB table did not trigger the page-table PSRAM fallback.
The large regression's precise cause was not isolated; the result does
not establish that table lookup itself accounts for the entire loss.

The candidate patch and reproducible checks are retained, while production
CPU source is restored to the committed baseline. The board receives the
exact previously tested baseline firmware, with interpreter SHA256
`05d946e3fad29dab88f699c4c0a8e4586385e594576d7c7d1598809a8b33940d`.

[Artifacts](measurements/immediate-table-2026-11-06/) include the patch,
helper and target-table checkers, CPU/differential results, identical host
replay, target table proof, runtime clock/page-table confirmation, initial
launch rejection and recovery output, all ten profiles, timing intervals,
model confirmations and fingerprints. Private matching ELFs, binaries
and full boot logs remain under `/tmp/acorn-immediate-table-2026-11-06/`;
ROMs, discs and boot/network logs are excluded from the repository.

After restoring the source, all 190 CPU checks pass and the rebuilt
interpreter matches the baseline byte for byte (43,154 bytes and the
same SHA256 above). The independently reproduced target-table check
matches the saved verification JSON exactly.

The original A3020/ARM250 at 12 MHz, RISC OS 3.11 and 4 MB RAM was
restored. Its final Lander check completed 1,503 frames in 30.043 seconds:
**50.029 FPS**, 100.058% real time. The emulator was reset and visually
verified at the 640x480 RISC OS desktop. The serial port was released.
